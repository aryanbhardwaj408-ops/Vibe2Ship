# Nudge AI — Product Brief and Requirements

> **Document status:** Current product summary for the repository. This document describes the intended behavior and known implementation boundaries; it is not a production-readiness or service-level guarantee.

## 1. Product overview

Nudge AI is a task-execution coach built for the Vibe2Ship hackathon. Its goal is to help a user move from a vague intention to a concrete plan and then make progress through that plan.

The product combines a conversational AI Coach with task management, a prioritized plan queue, focus tools, scheduling, snooze/resume actions, and progress feedback.

## 2. Core user journey

1. **Describe a goal.** The user enters a task or starts a conversation with the AI Coach.
2. **Clarify and plan.** The Coach can ask follow-up questions and organize one or more goals.
3. **Generate structured steps.** The browser sends a prompt to the backend at `POST /api/plan`. The backend calls Gemini with the server-side `GEMINI_API_KEY`.
4. **Review the plan.** The user can inspect and edit proposed steps before committing the plan.
5. **Execute.** The plan becomes a task. The user can complete steps, use focus timers, pause or snooze work, and resume later.
6. **Review progress.** The interface shows task status and activity/streak statistics.

If live AI planning fails or returns unusable structured output, the application can use built-in domain-specific fallback steps. The user experience should not imply that a fallback plan was generated by Gemini.

## 3. Current feature areas

### Planning and coaching

- Conversational AI Coach with follow-up/clarification flows.
- Handling of single-goal and multi-goal input.
- Structured task steps with supporting planning metadata where available.
- Review-before-start flow, including editing and removing proposed steps.
- A prioritized queue summary for plans containing multiple tasks.
- Domain-specific fallback plans when AI output cannot be used.

### Task execution

- Task states: pending, active, snoozed, and completed.
- Step-level completion tracking.
- Resume and snooze actions.
- Scheduling and focus/session time controls.
- Progress, activity, streak, and mood-related UI feedback.
- Browser-based speech-to-text where the browser supports and permits it.

### Persistence

- Tasks and associated progress are stored in browser `localStorage`.
- There is no account-based storage or cross-device cloud synchronization in the current architecture.
- Clearing browser data or changing browser/device can remove or separate the user's saved state.

## 4. Technical architecture

| Area | Current implementation |
| --- | --- |
| UI | Static HTML, CSS, and vanilla JavaScript |
| Frontend state | Browser memory and `localStorage` |
| Backend | Python and FastAPI |
| AI provider | Google Gemini API |
| AI endpoint | `POST /api/plan` |
| Health endpoint | `GET /api/` |
| Deployment definition in this repo | Render Blueprint in `render.yaml` |
| Tests | pytest, JavaScript syntax checks, GitHub Actions |

The frontend must not contain provider credentials. The backend reads `GEMINI_API_KEY` from its server-side environment and sends it to Gemini in the `x-goog-api-key` request header. `GEMINI_MODEL` selects the model and defaults to the value configured in the current backend.

The frontend calls the relative path `/api/plan`. Any deployment must route that path to the FastAPI service or a compatible server-side adapter. The repository provides a Render Blueprint; it does not currently include a Vercel-specific adapter/configuration. Any separate Vercel routing setup should be documented in the deployment instructions when it becomes part of the repository.

## 5. Reliability and security requirements

- **Secret management:** never commit real API keys, tokens, or a local `.env` file. Keep secrets in the backend hosting environment.
- **Failure handling:** handle missing credentials, upstream API errors, timeouts, invalid responses, and rate limiting without exposing secret values.
- **Input validation:** reject empty prompts and enforce a maximum prompt size at the backend boundary.
- **Output handling:** validate structured AI output and escape user/model-provided text before inserting it into HTML.
- **Basic abuse protection:** use a request limit for the demo API and document that an in-process limiter is not sufficient protection for scaled production deployments.
- **Observability:** test a live `POST /api/plan` response. A healthy `/api/` endpoint or visible fallback steps alone do not prove the Gemini integration is working.
- **Browser compatibility:** voice input depends on browser speech-recognition support and permissions.
- **Data clarity:** tell users that task persistence is browser-local and not backed by a user account.

## 6. Quality checks

The repository's GitHub Actions workflow should run on pushes and pull requests and cover:

- Python compilation checks for backend and test files.
- JavaScript syntax checks for `script.js` and `calendar.js`.
- The pytest suite, including API behavior, secret-boundary checks, error handling, and rate limiting.

Before publishing a release/demo update, manually verify the key user journeys: open the Coach, generate an AI plan, review/modify steps, start a task, complete a step, snooze/resume, reload to confirm browser-local persistence, and test the fallback behavior when AI is unavailable.

## 7. Known boundaries and possible future improvements

These items are opportunities, not claims about current functionality:

- Account-based persistence and cross-device sync.
- Drag-to-reorder the task queue.
- A more explicit estimated-finish-time summary.
- Calendar export for a planned task queue.
- Shared/distributed rate limiting and hosting-level abuse controls for a public production service.
- Clearer deployment automation/configuration for each supported hosting platform.

## 8. Implementation history

The project has evolved through iterations of the conversational Coach, task classification, multi-goal planning, clarification flows, and a prioritized queue with a single start action. The Git commit history is the source of truth for the exact implementation changes; this document intentionally focuses on the current product and architecture rather than treating old sprint notes as deployment instructions.
